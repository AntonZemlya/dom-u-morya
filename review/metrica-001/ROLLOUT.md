# METRICA-001 — один production-релиз с действующей аналитикой по согласию

Решение владельца от 03.11.2026: **не выпускать отдельную версию analytics OFF**.
Применяем один точный проверенный package с `analyticsEnabled=true`,
`operatorPolicyApproved=true`, `vendorPayloadReviewApproved=true` и счётчиком 113992596.
Этот документ описывает процедуру; сам по себе он не является доказательством её выполнения.

## Контракт пользователя и SEO

- До явного отдельного разрешения и успешного same-origin SQLite receipt: **0 запросов к Яндекс.Метрике**.
- «Продолжить без аналитики», отсутствие выбора и отзыв оставляют аналитику OFF.
- Согласие на отправку заявки версии `2026-10-31` независимо от аналитики и не меняется.
- Новая `consent-analytics.html` доступна людям через ссылки и баннер, но содержит
  `<meta name="robots" content="noindex,follow">` и не добавляется в sitemap;
  `robots.txt` сохраняет `Allow: /`.
- Версия юридического текста `analytics-2026-11-03-v2` совпадает в публичной HTML,
  неизменяемом текстовом файле и серверном PHP (SHA задаётся именно содержимым текста).
  180 дней действительности, затем/при отзыве до 30 дней хранения подтверждения —
  выбранный срок технического регламента, не универсальный юридический норматив.
- Счётчик создан; автоцели, Вебвизор, ecommerce, трекер контактов и отчёты рынка
  выключены в кабинете. Пять JS-целей без полей формы. Не использовать стандартный
  snippet/noscript-пиксель.

## Единый релиз: последовательные операции, один набор публичных изменений

1. Сверить точный новый `main` после принятого PR, clean worktree,
   SHA package, `ci:fast` и `ci:full`, read-only Jino preflight/plan.
   Scope — только публичные файлы METRICA-001. Не трогать другие сайты, SMTP,
   `.envrc`, существующие заявки, `.htaccess`, действующие бэкапы и настройки DNS.
2. До выкладки публичных файлов подготовить *приватную серверную зависимость*
   на Jino в выделенном namespace `.dom-u-morya/analytics/`, с
   `state/` и `runtime/` (каталоги 0700, PHP и база 0600, без симлинков).
   Поместить проверенные версии `expire.php`, `api/analytics-core.php` и
   `api/analytics-document.php` в private runtime, проверить SHA и PHP 8.4/SQLite3.
   Создать **только пустую** SQLite schema (ни одного вымышленного согласия),
   проверить DB 0600 и пустую таблицу. Приватная база должна быть вне web-root.
   Не копировать и не изменять базу Rehab Profi.
3. Получить свежий guard-план по Jino, выполнить предусмотренный package
   backup/verify и **один** `release apply` с analytics ON в одном публичном
   пакете. Не делать промежуточный пользовательский релиз OFF.
4. Выполнить штатную проверку manager `verified` + read-only HTTPS SHA и
   protected routes: helpers 404; GET consent endpoint 405; API формы остаётся
   ready, заявки не отправлять. Отдельный Chromium fresh context **без согласия**
   не должен обращаться к `mc.yandex.ru`; отказ/открытие юрдокументов тоже
   без vendor. Проверить, что ссылки и футер доступны на мобильном.
5. Проверить исполнение одобренного выбора в реальном браузере владельца
   при его сознательном нажатии «Разрешить аналитику»: одна серверная строка
   allow и загрузка реального счётчика; отказ и отзыв не создают скрытых
   посещений. Не имитировать согласие обычного посетителя и не отправлять
   тестовую заявку с реальным телефоном. Если реальный тест не выполнялся,
   фиксировать это честно и сохранять нулевые фактические визиты.
6. Настроить в панели Jino scoped ежедневную задачу
   `/opt/alt/php84/usr/bin/php <private-runtime>/expire.php --expire`,
   **после** проверки CLI, пути, таблицы и существующих заданий; не заменять
   чужие cron. Провести одну контрольную проверку выполнения с кодом выхода 0
   без печати или экспорта пользовательских записей.

## Fail-closed / rollback

- До подтверждённого разрешения локальное JS не исполняет сторонний tag.js.
  При недоступной SQLite, ошибках доказательства, неподдержанном host или
  сетевом сбое — *нет* аналитики, сайт и форма доступны.
- При ошибке выпуска: не повторять `apply` вслепую, смотреть
  `release status`; `awaiting_http_verify` допускает только штатный
  `finalize`. Публичный rollback — по сохранённому backup и точному GO.
- Mutable SQLite **никогда** не перезаписывается release-backup и не удаляется
  при откате публичного кода, чтобы сохранить уже зарегистрированные отзывы
  и доказательства до expiry. Не удалять архивы/legacy состояния автоматически.
- Отдельную систему offsite backups не создаём. Задача email-retention #18,
  другие сайты и настройки счетчика Rehab Profi вне scope.
