## Доставка и границы подтверждения

Одно письмо PHPMailer: From/envelope `sales@zhk-dom-umorya.ru`, To `info@anyara.ru`,
BCC `azm1982@yandex.ru`; один MAIL, два RCPT, один DATA. При отказе любого RCPT —
RSET и исключение до DATA. Нет второй отправки, fallback или автоматического retry.
BCC не записывается в видимые заголовки. Reply-To берётся только из проверенного
необязательного e-mail посетителя. Клиент не задаёт получателей.

GO A уже подтвердил Jino → Яндекс: Inbox, SPF=pass, DKIM=pass. Это свидетельство
транспорта и контрольного ящика. Основной ящик подтверждён владельцем по адресу,
но доставка туда не проверялась. Ни конфигурация, ни отчёт не объявляют её успешной.
Новый синтетический тест основного ящика исключён по решению владельца.

Новые совместные gates: FORM_ENABLED, SMTP_TRANSPORT_VERIFIED,
CONTROL_MAILBOX_VERIFIED=azm1982@yandex.ru, OWNER_CONFIRMED_TO=info@anyara.ru,
ACCEPT_UNTESTED_MAIN, LEGAL_APPROVED=2026-10-31, точные MAIL_TO/MAIL_BCC и
LEGAL_MAIL_TO/LEGAL_MAIL_BCC. Примеры конфигурации выключены. Старые
DELIVERY_VERIFIED и DELIVERY_VERIFIED_TO остаются false/пустыми;
MAIN_DELIVERY_VERIFIED=false. Финальный GO отдельно принимает непроверенную
доставку на основной адрес, разрешает контрольный доступ BCC и утверждает документы.

## Юридическая редакция и ручное хранение

Редакция `2026-10-31` синхронна в PHP, JavaScript и двух документах. Свободная
отдельная галочка обязательна, по умолчанию пуста. Сервер проверяет true и редакцию.
Служебный раздел письма хранит отметку, версию, способ и серверное время МСК до
секунды — то же значение, которое получает private state. ID остаётся в Message-ID,
ответе API и state; в теме и менеджерском тексте его нет. Письмо — временное
доказательство, не неизменяемый журнал. SQLite/cron/автоудаление не добавлены.

**Известное ограничение:** владелец сообщил, что провайдер и расположение хранения
info@anyara.ru пока неизвестны. В документах это прямо указано; Jino отвечает за
исходящий SMTP, Яндекс — за контрольный ящик. Утверждения о размещении основного
ящика на Jino/в РФ нет. Оператору необходимо установить реальные условия хранения,
доступа и удаления у обоих получателей и оценить их до утверждения юридической
редакции и GO. Готовность кода не подтверждает выполнение этих обязанностей.

Ручная процедура оператора (отложенная задача [Issue #18](https://github.com/AntonZemlya/dom-u-morya/issues/18)):

1. Ограничить доступ к обоим ящикам уполномоченными лицами; учесть рабочие пересылки
   и копии. Уточнить у каждого провайдера расположение и удаление резервных копий.
2. При завершении консультации/подбора или отзыве отметить событие и срок исполнения.
   Не хранить обращения бессрочно; отдельно документировать иной законный повод,
   если он действительно есть. Проверить запрос субъекта без избыточных данных.
3. При отсутствии иного основания удалить исходное письмо и BCC, пересылки,
   рабочие выгрузки, архивы, спам, корзины и удалённые у всех уполномоченных лиц;
   проверить резервные копии по условиям провайдеров. Обычно срок — не более
   30 дней после цели/отзыва с учётом применимых исключений статьи 21.
4. Зафиксировать уничтожение по применимому порядку. Предусмотренные приказом
   Роскомнадзора №179 акты и применимые выгрузки журналов хранятся 3 года после
   уничтожения; этот срок не относится к самим письмам-заявкам. Исключительные
   6 месяцев при невозможности уничтожения не являются общим сроком хранения.
5. Минимальный состав доказательства после удаления полного обращения требует
   отдельного решения оператора в #18; данный релиз такую базу не создаёт.

Источники для проверки норм: [152-ФЗ, официальный текст Минтруда](https://mintrud.gov.ru/docs/laws/130)
(статьи 5, 9, 18, 21), [разъяснение прокуратуры о приказе №179](https://epp.genproc.gov.ru/ru/proc_12/activity/legal-education/explain/e153603/).
Технические TTL: принятые запросы 24 часа, неопределённые/неудачные до 7 дней,
счётчики 10 минут. Это защита повторов, не срок хранения согласий.

## Применение после нового GO

Пакет закрепляет существующий snapshot после ручной SMTP-настройки:
SHA-256 `0083b86deb187949d5f9c20b39ace060fae66e82c9e92a37c736fcb737615b36`.
Перед первым изменением worker сверяет полный public inventory и config: SHA,
mode, uid/gid, mtime_ns и размер. Любое отличие — STOP. Новый snapshot можно получить
read-only командой `python3 -B ops/form_release.py snapshot`; он не подменяет
принятую baseline и не разрешает продолжение при расхождении.

После независимой приёмки владелец должен прислать **точную** строку `go` из
`go-prod.json`. Только после этого применяется команда (GO — несекретный текст):

```sh
python3 -B ops/form_release.py apply --go '<точная разрешённая строка GO PROD FORM>'
```

Контроллер ограничен SSH alias `rehab-profi-jino`, строгим known_hosts и фиксированным
`/home/users/j/j84938826/domains/zhk-dom-umorya.ru`. Последовательность:

1. Проверить SHA архива, control sources, точный GO и drift. Создать одноразовый
   каталог релиза; повторное применение того же SHA запрещено.
2. Приватно сохранить полный public-backup.tar (0600) и config-backup.php (0600),
   хеш backup в receipt; снова сверить baseline. Записи state и GO A markers не менять.
3. Установить/проверить runtime. Атомарно сохранить окончательный маршрут, но оставить
   FORM_ENABLED=false и все новые gates выключенными. Опубликовать только 7 файлов,
   lead-core последним, каждый через atomic rename.
4. Проверить `form-status.php`: enabled=false, ready=true, version=2026-10-31.
   `ready` проверяет PHP8.4/OpenSSL/ctype, pinned runtime, SMTP-настройки и state
   **без соединения с SMTP**, без создания state. Проверить страницы, deny dotfiles,
   GET lead=405 и заведомо некорректный POST `{}`=503; писем нет.
5. По уже полученному точному GO атомарно включить новые gates. Проверить enabled=true,
   ready=true; GET lead=405, POST `{}`=422. Ни в одном smoke нет валидной заявки.
6. Сохранить локальный execution.json и приватный receipt. При ошибке smoke контроллер
   выполняет fail-closed rollback; при неопределённом SSH stage — STOP, изучить receipt,
   не повторять apply вслепую. Дополнительные синтетические письма не разрешены.

После запуска контролировать фактические заявки в BCC и основной ящик отдельно,
проверять отказы/bounce в sales. BCC receipt не доказывает доставку основному ящику.
MAIN_DELIVERY_VERIFIED остаётся false, пока оператор не подтвердит фактический приём.

## Откат

```sh
python3 -B ops/form_release.py rollback --go '<та же разрешённая строка GO PROD FORM>'
```

Worker сначала атомарно выключает форму, проверяет хеш backup/config, восстанавливает
только scoped файлы из приватного backup, удаляет только 3 добавленных пути и сверяет
полный исходный public inventory (включая .envrc). Восстанавливает прежний config с
FORM_ENABLED=false. State, one-shot markers, полученные письма и общий runtime не
откатываются/не удаляются. SMTP уже принятые письма отозвать откатом невозможно.
Неизвестные изменённые scoped файлы не перезаписываются: STOP для ручного разбора,
форма остаётся выключенной. Backup сохраняется приватно для независимой проверки.

## Локальная проверка

```sh
SITE_URL=https://zhk-dom-umorya.ru npm run build:production
PHP84_BIN=/private/tmp/rehab-ci-php84/runtime/bin/php npm run test:form
PHP84_BIN=/private/tmp/rehab-ci-php84/runtime/bin/php PHP84_CGI_BIN=/private/tmp/dom-smtp-harness-php84/sapi/cgi/php-cgi npm run test:form-release
```

Release fixture использует одноразовые Apache TLS + настоящий PHP8.4 CGI,
проверяет backup → disabled → enable → rollback, drift config/public до записи,
частичный сбой публикации, неверный GO, tampered archive, symlink, сохранение HMAC,
STATE_DIR, пароля, state и markers, отсутствие wrapper и **нулевое число SMTP-соединений**.
Harness запрещает внешний DNS/TCP и SSH. SMTP QA отдельно использует TLS sink на
loopback с синтетическими данными. Исторический GO A harness не является разрешением
на новый тест. При подготовке допускается только read-only snapshot/GET; выполненная сверка
подтвердила совпадение 243 public файлов/config и enabled=false. Изменяющие команды
Jino в подготовке не выполняются.
