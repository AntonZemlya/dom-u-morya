# Релиз: универсальный менеджер

Только `zhk-dom-umorya.ru`, SSH alias `rehab-profi-jino`, фиксированный home из существующей конфигурации проекта. Код: `release_manager.py` (локальная CLI/HTTPS),
`release_core.py` (stdlib Python 3.6 на Jino), `release-policy.json`.
Привязок к историческим FORM commit/package/baseline в новом менеджере нет.

## До GO: только чтение сервера

1. Из актуального main создайте одну ветку/worktree, внесите изменения, выполните
   `ci:fast` и `ci:full`, проведите review, закоммитьте. Main не менять без owner merge GO.
2. Постройте пакет из полного SHA commit. Используется чистый `git archive`,
   production origin, явный allowlist, зафиксированный Composer runtime; ignored dist
   и незакоммиченные файлы не входят. Необходимы установленные npm/vendor dependencies.
3. Проверьте архив независимой повторной сборкой. Формат содержит manifest,
   public и несекретный private SMTP runtime; config/state в пакет не входят.
4. В панели Jino прочтите текущую квоту и использование. Сохраните локально
   `.release-output/quota.json` с `source: "Jino panel"`, `observed_unix` (UTC epoch),
   `limit_bytes`, `used_bytes`. При округлённых значениях используйте меньший limit
   и больший used. Измерение старше 24 часов блокирует apply. `df` используется
   лишь как дополнительный ограничитель свободного места файловой системы.

```sh
npm run release -- build --commit FULL_COMMIT
npm run release -- verify --archive ARCHIVE --sha PACKAGE_SHA256
npm run release -- preflight --archive ARCHIVE --sha PACKAGE_SHA256 --quota-evidence .release-output/quota.json --output .release-output/preflight.json
npm run release -- plan --release-id release-YYYYMMDD-N --archive ARCHIVE --sha PACKAGE_SHA256 --quota-evidence .release-output/quota.json --output .release-output/plan.json
npm run backup -- list
npm run backup -- prune --dry-run --output .release-output/prune.json
```

JSON-файлы, используемые как `--plan`, создавайте прямым `python3 ... --output ...`;
не перенаправляйте stdout `npm run` в JSON: npm добавляет свои служебные строки.
Все output в примерах — локальные файлы. SSH worker исполняется из памяти с `-B`;
не загружает скрипты, не создаёт lock/каталоги на read-only этапах.
Preflight сверяет SSH inventory, modes/owners, `.envrc`, config и SMTP runtime,
HTTPS/TLS/DNS, enabled/ready, API GET 405 и dotfile 403/404. Никаких POST.
Plan содержит полный baseline, точный add/replace/delete diff, commit, package SHA,
policy/inventory SHA и SHA-256 канонического JSON с подтверждением квоты.
Сохраните исходные пакет, план, файл квоты и строку GO вместе. Поле `http_profile`
показывает итог выбора профиля с учётом локальной истории Git, а `http_profile_reason` —
причину. При отсутствии diff он возвращает `action=noop`, `go=null`:
такой план нельзя применить, резервная копия не создаётся.

## Точный GO и применение

Владелец рассматривает полный план, CI, scope и риски и отдельно пишет строку
`go` из JSON, например:

`GO APPLY zhk-dom-umorya.ru RELEASE_ID PACKAGE_SHA256 PLAN PLAN_SHA256`

Запрос разработки, SHA сам по себе и старые GO не разрешают запись. CLI проверяет
полное совпадение; подставлять эту строку без реально полученного GO нельзя.
После разрешения оператор запускает:

```sh
npm run release -- apply --archive ARCHIVE --sha PACKAGE_SHA256 --plan .release-output/plan.json --quota-evidence .release-output/quota.json --go 'EXACT_OWNER_GO'
```

Apply получает общий flock, перепроверяет snapshot, inventory, policy, quota и
каждый изменяемый файл. Создаёт один приватный release ID 0700, пакет/plan/receipt
0600, один backup публичного baseline, config и активного SMTP runtime. Backup
связан с исходным production и новым package SHA; архив проверяется по SHA,
составу и permissions, затем разворачивается в отдельную rehearsal-папку внутри
авторизованной подготовки и сравнивается. Только после этого начинается публикация.
State заявок не читается и не резервируется. Неизвестные файлы, symlink/hardlink,
повреждённые tar, traversal, чужие владельцы и незавершённые релизы блокируют запись.

Менеджер принимает только точные разрешённые редакции `.htaccess`. Для статического сайта
используется редакция v3 PAGESPEED-MOBILE-001, закреплённая SHA-256:
`1412dd94ca93a9942cb0f679472294925496ca12c3e4317484b09e3c5f98504a`.
Наличие маркера или отдельной запрещающей директивы не заменяет точный SHA.
Произвольные изменения policy по-прежнему блокируют package verify и preflight.

Поддерживаются следующие точные переходы к v3:

- v1: `652ea884d02b2a73b7fa026823c4732fd1ccccba1ba11e1c43ee8c19be0e3ee5`,
  scope SEO-REDIRECT-001;
- v2: `86a28fe3e086dc73b1e901277080e79df5fbe0e178fcf5644b5a2c7437f877c7`,
  scope PAGESPEED-MOBILE-001;
- цель обеих миграций — точная v3. В плане меняется только `.htaccess`;
  любой дополнительный add/replace/delete блокирует план;
- план содержит оба SHA и scope, связанные общим plan SHA и прежним exact GO;
- backup/rehearsal и rollback сохраняют исходные bytes/metadata;
- v1/v2 допустимы только при чтении baseline, исторических receipts и backup/rollback.
  Новые пакеты принимают только v3. Архивный Jino rollout остаётся заблокированным.

Для этих исторических baseline разрешён только соответствующий точный переход.
План перехода и пакет обычного релиза проверяются и согласуются отдельно.

Для каталога PRICE-SYNC-002 принимается точная редакция v4
`4fcb98daec1c53d3b5829a9731c202e614d9d83080e67a784a66014a27eb7758`.
Переход из v3 связан с обязательным набором файлов каталога и точным GO плана.
Менеджер публикует новое правило после кода и шаблона. В последующих релизах
v4 не меняется. Приватные данные Cron отделены от контрольных сумм релиза.
Проверка главной страницы после подключения Cron проверяет шаблон и согласованность
динамического снимка. [Порядок установки и отката каталога](CATALOG-SYNC-RUNBOOK.md).

Статический кэш: HTML, CSS, JS и файлы с постоянными URL имеют `max-age=0,
must-revalidate`; длительный `immutable` разрешён только новым WebP/WOFF2 с SHA-256
содержимого в имени. PHP/API/JSON не охвачены директивами. Проверка на реальном
локальном Apache: GET/HEAD/304, изменение файла по старому URL, ошибки и API `no-store`.
При обновлении изображений/шрифтов запустить `node scripts/generate-performance-assets.mjs`,
обновить HTML srcset, затем `npm run content`. Генератор сохраняет прежние опубликованные
хеш-URL в `data/performance-assets.json` (`retained`); их удаление — отдельное решение.

Постоянный dotfile guard сохранён побайтно; ACME не перенаправляется. DirectorySlash
остаётся включённым, listing запрещён. Правило реальных каталогов формирует HTTPS
раньше mod_dir; `/privacy/` остаётся каталогом, а `/privacy.html` — документом.
Редиректы www на стороне nginx Jino предшествуют Apache и могут добавлять один hop.
По решению владельца в SEO-REDIRECT-001 сохранено единственное исключение:
`http://www.DOMAIN/path?query` → `http://DOMAIN/path?query` → canonical HTTPS,
оба ответа 301, промежуточный HTTP не отдаёт страницу сайта. Другие HTTP Location,
любые HTTPS→HTTP и циклы запрещены. Настройки панели и nginx не меняются.
Для отдельной диагностики полная GET/HEAD матрица доступна через
`python3 -B ops/url_matrix.py --output HTTP_REPORT.json`. Команда обращается
к production и рассчитана на отдельный согласованный прогон.

Index публикуется последним, каждый файл
через fsync + atomic replace. `.envrc`, config, установленный runtime, DNS/SSL
не изменяются. SMTP dependency migration намеренно требует отдельного review:
при смене публичного runtime descriptor или установленных runtime bytes STOP.
Такая миграция не может быть замаскирована обычным website release.

Запись по файлам не обеспечивает атомарный switch всего сайта: краткий смешанный
набор возможен; меняйте совместимые ресурсы, для переименований используйте двухфазный
релиз (сначала добавить новые assets, затем удалить старые отдельным релизом).
Все операторы должны пользоваться этим lock; изменения через панель/FTP во время
релиза запрещены процедурой, внешние процессы не обязаны уважать flock.

## Verify, статус, потеря ответа

Движок по-прежнему сверяет SHA-256 и метаданные всех опубликованных файлов
через SSH. Профиль HTTP выбирается автоматически.

- **`compact`** применяется для совместимых замен интерфейса и контента, а также
  для добавления типовых статических ресурсов в существующие каталоги `assets`.
  Текущий receipt должен совпадать с полным серверным снимком. Его цепочка
  подтверждений должна восходить к полной HTTP-проверке за последние семь дней.
  Менеджер сверяет историю Git от commit этого receipt до commit пакета.
  По HTTPS проверяются затронутые файлы, главная и три юридические страницы.
  Ещё 28 сценариев проверяют канонический переход с сохранением query, 404,
  запрет просмотра каталогов, закрытые файлы и GET-защиту API.
- **`full`** проверяет всю HTTP-доступную статику и 236 сценариев матрицы.
  Он выбирается при изменении `.htaccess`, PHP, кода релизов или безопасности,
  удалении файлов, новых маршрутах, недоступной истории Git и недостаточном
  подтверждении предыдущего релиза. Любое изменение `privacy/privacy.js` требует
  `full`, поскольку файл управляет согласием и включением аналитики.
  Расхождение текущего receipt с серверным снимком останавливает релиз до выяснения
  причины.

Оба профиля проверяют готовность формы, запреты на прямой доступ к обработчикам
и, для PRICE-SYNC-002, заголовки шаблона, статус и версию динамического снимка,
а также согласованность данных HTML и цен в JSON-LD. Главная страница
со встроенным каталогом сверяется с SHA-256 шаблона. Все обращения — GET/HEAD.

Общий HTTP-клиент выдерживает интервал не менее 90 мс между началами запросов.
Для типизированных временных обрывов есть до трёх повторов с задержками
0,25 / 0,5 / 1 с. Лимит в `compact` — 65 попыток или 30 с, в `full` —
850 попыток или 360 с. В лимит входят переходы и повторы. Тайм-аут отдельного
сетевого обращения ограничен 15 секундами и остатком общего времени.
Сертификат TLS, HTTP-статус, Location, SHA-256, утечка закрытого файла и
несогласованный каталог останавливают проверку сразу. Публикация и
SSH-операции не повторяются автоматически.

20.11.2026 успешная HTTP-проверка заняла 208,74 с. В матрице было 491 обращение
и семь сетевых повторов. В том прогоне интервал 90 мс применялся только к
матрице. Если заложить его целиком дополнительно для 293 обращений за её
пределами, получится около 235 с. Лимит 360 с оставляет запас на более медленные
ответы и повторы. Интервал и предел числа обращений действуют независимо
от времени. [Замеры инцидента](https://github.com/AntonZemlya/dom-u-morya/pull/42#issuecomment-7043087544)

```sh
npm run release -- status --release-id RELEASE_ID
```

При `awaiting_http_verify` используйте исходный пакет, точный план,
первоначальное разрешение владельца и тот же файл квоты.

```sh
npm run release -- finalize --archive ARCHIVE --sha PACKAGE_SHA256 --plan .release-output/plan.json --quota-evidence .release-output/quota.json --go 'EXACT_ORIGINAL_OWNER_GO' --output .release-output/http-result.json
```

Для `finalize` явно укажите `--quota-evidence`, даже если квота записана в файле
политики. Проверяется SHA исходной политики с этим содержимым квоты. Возраст
наблюдения проверялся при `apply`. Для завершения нужна исходная запись,
даже если с тех пор прошло более 24 часов. При расхождении CLI выводит ожидаемые
SHA. Для прежних планов доступен только SHA политики.

До HTTP и перед записью `verified` движок проверяет текущий release ID,
пакет, исходный план, backup и опубликованный снимок. `finalize` записывает
результат проверки в receipt и не публикует файлы. При исчерпании сетевых повторов
проверенные SHA статических файлов могут сохраниться в закрытом receipt на 15 минут,
пока снимок и запись релиза совпадают. Главная, юридические страницы, readiness
и маршруты проверяются заново. При жёстком завершении процесса до записи прогресса
`finalize` начинает HTTP-проверку с начала. Если потерян SSH-ответ, сначала
проверьте `status`. Release ID после публикации занят постоянно.

Отчёт содержит профиль и причину выбора, число запросов, повторов и сетевых ошибок,
прочитанные байты, время, количество проверенных и повторно использованных файлов,
маршруты и итоговый статус. `--output` сохраняет отчёт об успешной проверке либо STOP
на этапе HTTP или записи подтверждения. Тела закрытых ресурсов и параметры query
в отчёт релиза не попадают.

Если файл скопирован частично или случилась ошибка записи при живом worker, движок
пытается восстановить только scoped public files из проверенного backup. Любой
drift либо ошибка восстановления оставляет `recovery_required`; слепой retry запрещён.
При жёстком завершении worker receipt остаётся `publishing`/`rolling_back`; используйте
[RECOVERY.md](RECOVERY.md). Mutable state не откатывается.

## Переход на новую версию менеджера

После независимой приёмки проверьте текущие release IDs через `status` и
сохраните вместе исходные планы, пакеты, файлы квоты и разрешения владельца.
Действующие подтверждённые receipts и backup читаются в прежнем формате.
Для прежнего плана без полей профиля применяется `full`. Если уже опубликованный
пакет меняет `privacy/privacy.js`, `finalize` также проведёт `full` с исходным планом
и GO, даже если в плане был указан `compact`.

Изменения только в менеджере дадут `noop` при совпадающих публичных файлах.
Для первого согласованного изменения сайта после смены менеджера ожидайте
`full`, если diff от последнего опубликованного commit содержит код менеджера.
Следующее небольшое совместимое изменение может использовать `compact`
после полной успешной проверки. Для каждого `apply` нужны CI и отдельное
полное разрешение владельца на пакет и план.
